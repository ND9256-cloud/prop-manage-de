# Task 1.5e-prompt — Kaution synonym hints in mietvertrag schema

Task type: t1 S (single YAML edit + regenerate + verify, low risk surface)

## Why this task exists

Task 1.5g shipped clean per-page OCR with rate limiting. Both reference mietverträge (Lena Everding, Julija Paul) now have complete OCR text that includes the Kaution clause. Verified:

- **Lena**: 48,906 chars OCR, `mentions_kaution: YES`, `mentions_mietsicherheit: YES`. The clause is `"Der Mieter hat eine Mietsicherheit in Form einer Barkaution in Höhe von . . . . . . **1.950,00 Euro** zu leisten"`.
- **Paul**: 28,040 chars OCR, `mentions_kaution: YES`. The clause is `"§ 4 Kaution: 1. Der Mieter verpflichtet sich, eine Kaution in Höhe von _________________1100,00 € an den Vermieter zu leisten"`.

Despite both clauses being in OCR, Sonnet's Step 8b returns `kaution: { absence_state: "absent", confidence: "low", evidence: [], normalized_value: null }` for both contracts.

Hypothesis: the current schema's `kaution` field prompt fragment only mentions the literal word "Kaution". When the actual contract uses synonyms (Mietsicherheit) or wraps the amount in form-template noise (underscores, dotted lines), Sonnet doesn't connect them. This is a prompt-engineering gap, not an OCR gap and not a model capability gap.

The fix is to teach the schema prompt to look for the family of related terms and the common formatting patterns.

## Goal

After this task lands and the Edge Function redeploys:
- Re-extract Lena → `kaution: { absence_state: "present", normalized_value: 195000, evidence: [...] }`
- Re-extract Paul → `kaution: { absence_state: "present", normalized_value: 110000, evidence: [...] }`

If this works on both reference cases, prompt synonyms are sufficient — no verifier needed for kaution.

If it works on only one (or neither), the bigger structural fix (missed-content verifier) becomes the next priority. This task is the cheap, narrow test.

## Design

### What the current schema probably says

I don't have the exact current YAML in this brief, but the `kaution` field was added in Task 1.5c with a German label and `monetary-verbatim` verifier. The extraction hints likely just say something like "Die Kaution (Sicherheitsleistung) des Mieters."

### What it should say (proposed text — implementer should adapt to match the existing schema YAML's style)

For the `kaution` field's `description` or `extraction_hint` (whichever key the schema uses for prompt guidance), expand to roughly this in German:

```
Kaution oder Mietsicherheit, vom Mieter beim Vermieter zu hinterlegen.

WICHTIG: In deutschen Mietverträgen erscheint dieses Konzept unter verschiedenen Bezeichnungen — alle bezeichnen denselben Sachverhalt:
- "Kaution"
- "Mietsicherheit"
- "Barkaution"
- "Sicherheitsleistung"
- Auch Kombinationen wie "Mietsicherheit in Form einer Barkaution"

Der Geldbetrag erscheint oft in Vorlagen mit umgebenden Unterstrichen, Punkten oder Strichen, etwa:
- "__________1.100,00 €"
- ". . . . . . . 1.950,00 Euro"
- "in Höhe von _____ Euro"

Suche im gesamten Dokument nach diesen Bezeichnungen und extrahiere den genannten Betrag, unabhängig von der umgebenden Formatierung. Der Betrag ist real auch dann, wenn das Vertragsformular Leerstellen oder Platzhalter um die Zahl herum aufweist.

Falls KEINE dieser Bezeichnungen im Dokument vorkommt, setze absence_state: "absent".
Falls die Bezeichnung vorkommt aber kein Betrag genannt wird, setze absence_state: "ambiguous" mit einer Erklärung.
```

The implementer should:
1. Read the current schema YAML
2. Locate the `kaution` field
3. Replace its description (or whichever key carries the prompt fragment) with the expanded text above, adapted to fit the existing schema's structural conventions
4. Bump the schema version: `2026-05-13-v1` → `2026-05-21-v1`

### Schema version bump

The schema version is what triggers regeneration of envelopes when the pipeline re-extracts. The current Lena and Paul envelopes are on `2026-05-13-v1`. After the version bump, re-queued extractions will produce envelopes on `2026-05-21-v1` — easy to distinguish from old runs.

### 5. Three outcomes

**Outcome A (both work):** Phase 1 ready. Update memory: Task 1.5e-prompt sufficient, verifier task deprioritized. Proceed to Task 1.7 (claim emitter).

**Outcome B (one works, one doesn't):** Document which one and look at why. Likely tells us something specific about the prompt — maybe one synonym was missing, or the form-template pattern in the failing contract is different. Iterate the prompt one more time, OR build the verifier as the more general answer.

**Outcome C (neither works):** Prompt synonyms are not the answer. The miss is something structural about how Sonnet treats absence on this field. Build the verifier (Task 1.5e-verifier) as the priority.

In all three outcomes, update memory with the result so we don't re-investigate later.
